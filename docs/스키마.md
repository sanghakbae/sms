# 데이터 스키마

Firestore 단일 저장소. 인증은 Google OAuth 하나뿐이고, 권한 판정은 **이메일**로만 한다.

컬렉션 이름에는 `VITE_COLLECTION_PREFIX` 접두사가 붙는다 (`src/firebase.js`의 `collectionName()`).
접두사가 비어 있으면 아래 이름 그대로다.

---

## 공통 필드

모든 문서에 담당자 정보가 붙는다 (`store.js` → `ownerFields()`).

| 필드 | 타입 | 설명 |
|---|---|---|
| `owner` | string | Firebase Auth uid. 권한 판정의 기준 |
| `ownerName` | string | 표시용 이름 (Google displayName, 없으면 이메일 아이디) |
| `ownerEmail` | string | 소문자 정규화된 이메일. 팀원 집계·목표 할당의 키 |
| `createdAt` | Timestamp | `serverTimestamp()` |
| `updatedAt` | Timestamp | `serverTimestamp()` |
| `teamId` | string | 소속 팀. **팀별 격리의 기준** |

`owner*` 는 클라이언트가 써 넣지만 보안 규칙이 `owner == request.auth.uid` 를 강제한다.
담당자 변경(재배정)은 관리자만 가능하다.

> [!warning] `teamId` 는 규칙만으로 걸러지지 않는다
> **보안 규칙은 필터가 아니라 검사다.** 팀원이 컬렉션 전체를 구독하면 남의 팀 문서
> 하나 때문에 쿼리가 통째로 거부된다. 그래서 클라이언트가
> `where('teamId','==',내팀)` 으로 좁혀 보낸다(`store.js` → `subscribeCollection`).
> 관리자는 필터 없이 전체를 받는다.
>
> 이 때문에 규칙의 read 조건은 `resource.data.teamId` 를 **직접** 비교한다.
> `data.get('teamId','')` 로 쓰면 Firestore 가 쿼리 조건과 짝지어주지 못해 목록이 막힌다.
>
> 그리고 이 쿼리에는 복합 인덱스가 필요하다 — `firestore.indexes.json` 을 배포하지 않으면
> 팀원 화면이 `failed-precondition` 으로 빈다.

## `customers` — 거래처

목록 정렬: `name` 오름차순.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `name` | string | ✅ | 거래처명. 규칙에서 비어 있지 않은 문자열임을 검증 |
| `industry` | string | | 업종 |
| `grade` | `'A'\|'B'\|'C'` | | 등급. 기본 `'B'` |
| `contactName` | string | | 고객사 담당자 |
| `phone` | string | | 연락처 |
| `email` | string | | 이메일 |
| `memo` | string | | 특이사항·니즈·히스토리 |

등급 정의는 `src/lib/pipeline.js` → `GRADES`.

- `A · 핵심` / `B · 일반` / `C · 관리`

**삭제 시 연쇄 삭제가 없다.** 거래처를 지우면 연결된 딜·활동의 `customerId` 가 고아가 된다.
UI 는 삭제 전에 끊기는 건수를 알려주고, 딜·활동은 `customerName` 을 복제 저장해 두어
이름은 계속 보인다.

## `deals` — 영업기회

목록 정렬: `updatedAt` 내림차순.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `title` | string | ✅ | 제목. UI 에서만 검증 (규칙에는 없음) |
| `customerId` | string | | 거래처 문서 id. 미선택 시 `''` |
| `customerName` | string | | 거래처명 복제. 거래처가 지워져도 남는다 |
| `serviceId` | string | | 대상 서비스 id (`settings/services`) |
| `serviceName` | string | | 서비스명 복제. 목록에서 지워져도 남는다 |
| `amount` | number | ✅ | 예상 금액(원). 규칙에서 `number && >= 0` 검증 |
| `stage` | string | ✅ | 영업 단계 (아래) |
| `lost` | boolean | | 실패 플래그. 단계와 **독립** |
| `lostReason` | string | | 실패 회고. `lost` 면 UI 에서 필수 |
| `expectedClose` | `'YYYY-MM-DD'` | | 예상 마감일. 미정이면 `''` |
| `closedDate` | `'YYYY-MM-DD'` | | 실제 종료일. 진행 상태로 되돌리면 `''` |
| `memo` | string | | 진행 상황, 경쟁사, 결정권자 |
| `payments` | array | | 입금 내역 `[{ id, date, amount, memo }]` |

### 입금 (`payments`)

수주는 '계약이 끝났다' 는 뜻이지 '돈을 받았다' 는 뜻이 아니다.
선금·중도금·잔금으로 나눠 들어오는 게 보통이라 한 줄씩 쌓는다.

별도 컬렉션으로 빼지 않은 이유 — 항목이 몇 개 안 되고, 딜을 고칠 수 있는 사람과
입금을 적을 수 있는 사람이 같다. 권한을 따로 걸 이유가 없으면 문서를 쪼개지 않는다.

판정은 `src/lib/settlement.js` 가 한다.

| 상태 | 조건 |
|---|---|
| `unpaid` 미입금 | 입금 합계 0 |
| `partial` 부분입금 | 0 < 입금 합계 < 수주액 |
| `paid` 완납 | 입금 합계 ≥ 수주액 |

### 단계 (`STAGES`)

순서대로 진행하고 `won` 이 마지막이다.

| id | 라벨 | 확률 | 비고 |
|---|---|---|---|
| `contact` | 상담 | 30% | |
| `proposal` | 제안 | 50% | |
| `negotiation` | 협상 | 80% | |
| `won` | 수주 | 100% | `closed`, `win` |

**설계 결정이 스키마에 박혀 있다.**

1. **실패는 단계가 아니라 플래그다.** 제안에서 깨질 수도, 협상에서 깨질 수도 있다.
   `stage` 를 그대로 두고 `lost: true` 를 붙이므로 "어디서 죽었는지"가 남는다.
   단계별 이탈 분석(`stageBreakdown`, `stageFunnel`)이 이걸로 돌아간다.

이전 버전의 `lead`·`qualify` 값은 삭제하지 않고 화면과 집계에서 `contact`(상담)로
정규화한다. 해당 문서를 수정해 저장하면 실제 값도 `contact`로 바뀐다.

판정 함수는 모두 `src/lib/pipeline.js` 에 있다 — `isDealWon`, `isDealOpen`,
`isQualified`, `dealProbability`.
`lost` 가 붙으면 `stage` 가 `won` 이어도 수주가 아니고, 확률은 0% 다.

### `closedDate` 규칙

단계나 `lost` 가 바뀔 때만 기록한다 (`Deals.jsx` → `submit`, `moveTo`).

- 종료(`won` 또는 `lost`)로 가면 → 기존 값이 없을 때 오늘 날짜
- 다시 진행 단계로 오면 → `''`

집계는 `closedDate` 를 우선 쓰고 없으면 `expectedClose` 로 대체한다 (`stats.js` → `closedMonth`).

## `activities` — 영업 활동

목록 정렬: `date` 내림차순. 작성자·팀장·관리자가 수정할 수 있다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `type` | string | 활동 종류 (아래). 기본 `'visit'` |
| `customerId` | string | 거래처 id. 미선택 시 `''` |
| `customerName` | string | 거래처명 복제 |
| `date` | `'YYYY-MM-DD'` | 활동일. 기본 오늘 |
| `note` | string | 논의 내용, 다음 액션 |

종류 (`ACTIVITY_TYPES`): `visit` 방문 🚗 · `call` 전화 📞 · `email` 메일 ✉️ ·
`meeting` 미팅 🤝 · `etc` 기타 📝

### `activities/{id}/comments/{cid}` — 팀장 피드백

| 필드 | 타입 | 설명 |
|---|---|---|
| `text` | string | 내용(마크다운). 1~2000자 |
| `owner`·`ownerName`·`ownerEmail` | | 작성자 |
| `createdAt`·`updatedAt` | Timestamp | |

**다는 것은 팀장 이상만, 읽는 것은 같은 팀이면 누구나.**
팀원이 자기 활동에 달린 피드백을 봐야 뜻이 있다.

활동 문서에 배열로 넣지 않고 하위 컬렉션으로 나눈 이유 — 작성자가 자기 활동을 수정할 때
팀장 댓글까지 덮어쓰지 못하게 하려는 것이다.

## `settings/*` — 설정 문서 4개

컬렉션이 아니라 **고정 id 문서 4개**다. 읽기는 팀원 전체, 쓰기는 관리자만.

### `settings/targets` — 연 매출목표

```js
{ "2026": 1200000000 }   // { 'YYYY': 금액 }
```

`setYearlyTarget(year, amount)` 이 `merge: true` 로 해당 연도 키만 갱신한다.

### `settings/ownerTargets` — 영업자별 목표 할당

```js
{ "2026": { "qa@muhayu.com": 400000000 } }   // { 'YYYY': { 이메일: 금액 } }
```

키는 정규화된 이메일이고 `0` 이하는 저장하지 않는다.
저장 시 **그 해 전체를 통째로 덮어쓴다** — 0으로 지운 항목이 남지 않게.

팀 목표와의 차이는 `allocationSummary` 가 계산한다. 팀원 목록에 없는 이메일에
남은 할당은 `orphan` 으로 따로 합산해서 총액이 어긋나지 않게 한다.

### `settings/admins` — 관리자 명단

```js
{ emails: ["someone@example.com"] }
```

여기에 더해 코드에 박힌 `BOOTSTRAP_ADMINS` 가 있다 (`src/lib/accounts.js`).
명단을 잘못 비워 아무도 못 들어가는 상황을 막는 안전장치라 화면에서 지울 수 없다.
최종 관리자 판정 = `BOOTSTRAP_ADMINS` ∪ `settings/admins.emails`.

### `settings/teams` — 팀 목록

```js
{ items: [{ id: "team_ab12cd", name: "대학영업 1팀" }] }
```

`id` 는 이름과 무관하게 만든다 — 팀 이름을 바꿔도 소속과 목표가 유지되도록.

### `settings/teamTargets` — 팀별 연 목표

```js
{ "2026": { "team_ab12cd": 800000000 } }   // { 'YYYY': { teamId: 금액 } }
```

전사 목표(`settings/targets`)를 팀에 나눈 것. 지워진 팀에 남은 목표는
`teamAllocationSummary` 가 `orphan` 으로 따로 세어 총액이 어긋나지 않게 한다.

### `settings/services` — 판매 대상 서비스 카탈로그

```js
{ items: [{ id: "plagiarism", name: "표절검사" }] }
```

`id`·`name` 이 둘 다 있어야 저장된다. 딜에는 `serviceName` 을 복제해 두므로
카탈로그에서 서비스를 지워도 기존 딜의 표기는 유지된다.

## `members` — 팀원 명단

문서 id 는 Firebase Auth uid.

| 필드 | 타입 | 설명 |
|---|---|---|
| `email`·`name`·`photoURL` | string | Auth 토큰에서 온 신원 정보 |
| `teamId` | string | 소속 팀. `''` 이면 미배정 |
| `role` | `'leader'\|'member'` | 팀 안에서의 권한 |
| `createdAt`·`lastLoginAt` | Timestamp | |

**로그인하면 본인이 자기 문서를 올린다** (`store.js` → `registerMember`). 신규 사용자는
`settings/teams.defaultTeamId`로 지정된 `배지터` 팀에 자동 배정된다. 기본 팀이 없으면
미배정으로 남는다.

생성 후 `teamId` 와 `role` 은 본인이 못 바꾼다 — 규칙에서 막는다. 최초 생성 시에도
관리자가 설정한 기본 팀만 허용하므로 임의의 팀으로 들어갈 수 없다.

**`teamId` 가 비어 있으면 그 자체가 '미승인' 이다.** 승인 플래그를 따로 두지 않는다 —
상태가 둘로 나뉘면 '승인됐지만 팀이 없는 사람' 같은 애매한 칸이 생긴다.

### 옛 데이터의 담당자

`members` 문서가 없는데 데이터에만 남은 담당자도 화면에는 나온다
(`teams.js` → `memberRows`, `registered: false`). 목록에서 잃어버리면 그 실적이
사라진 것처럼 보이기 때문이다. 다만 팀에 넣을 수는 없다(uid 가 없다).

집계 키는 여전히 `ownerEmail || owner` — 목표 할당이 이메일 기준이라 이메일이 사실상 주키다.

## 권한 3단

```
관리자  ─ settings/admins + BOOTSTRAP_ADMINS (이메일로 판정)
  └ 팀장  ─ members/{uid}.role === 'leader'
      └ 팀원 ─ 그 밖의 배정된 사용자
```

관리자는 이메일로, 팀장·팀원은 명단 문서로 판정한다. 왜 갈랐나 — 관리자는 팀이 없어도
전사를 봐야 하고(초기 세팅), 팀장은 '어느 팀의' 팀장인지가 있어야 뜻이 생긴다.

| | 관리자 | 팀장 | 팀원 |
|---|---|---|---|
| 거래처·영업현황 읽기 | 전사 | 전사 | 전사 |
| 활동 읽기 | 전사 | 자기 팀 | 자기 팀 |
| 만들기 | 자기 팀으로만 | 자기 팀으로만 | 자기 팀으로만 |
| 남의 문서 수정·삭제 | ○ | 자기 팀 안에서 ○ | ✗ |
| 활동 피드백(댓글) | ○ | ○ | 읽기만 |
| 팀 편성·역할 지정 | ○ | ✗ | ✗ |
| 목표(전사·팀·영업자) | ○ | ✗ | ✗ |
| 감사 로그 열람 | ○ | ✗ | ✗ |

- **팀원**(`isMember`) = 로그인 + `email_verified == true`.
  `ALLOWED_DOMAINS` 가 빈 배열이라 현재 **도메인 제한이 없다** — 인증된 Google 계정이면 누구나
  로그인은 된다. 다만 팀에 배정되기 전에는 아무 데이터도 보거나 만들 수 없다.
- **팀·담당자 이동**은 관리자만 (`teamUnchangedOrAdmin`, `ownerUnchangedOrAdmin`).
- **관리자라도 팀이 없으면 데이터를 만들 수 없다** — `createsInMyTeam()` 이 `hasTeam()` 을
  요구한다. 화면에서도 '+' 버튼을 잠근다.
- 그 외 모든 경로는 `allow read, write: if false`.

`firestore.rules` 와 `src/lib/accounts.js` 는 **같은 규칙을 중복 구현**한다.
한쪽만 고치면 어긋나므로 항상 함께 수정할 것.

## `auditLogs` — 감사 로그

| 필드 | 타입 | 설명 |
|---|---|---|
| `action` | string | `audit.js` 의 ACTIONS 값 |
| `actor`·`actorName`·`actorEmail` | | 실행자. 규칙이 본인으로 강제 |
| `teamId` | string | 실행자의 소속 |
| `targetId`·`targetLabel` | string | 대상 |
| `from`·`to`·`note` | string | 무엇이 무엇으로 |
| `at` | Timestamp | |

**덧붙이기 전용** — `allow update, delete: if false`. 읽기는 관리자만.

무엇을 남기나: 삭제, 권한 변경, 팀 편성, 목표 변경, 입금.
딜 하나 고칠 때마다 적으면 로그가 잡음이 되어 정작 볼 때 못 찾는다.

> [!warning] 위변조 불가 로그가 아니다
> 브라우저에서 쓴다. 고치거나 지울 수 없게 막았고 작성자도 본인 uid 로 강제되지만,
> 애초에 로그를 남기지 않고 요청만 보내는 것까지는 막지 못한다(그 요청 자체는 다른
> 규칙이 막는다). 진짜 위변조 불가 로그가 필요하면 Cloud Functions 에서 써야 한다.

## 인덱스

`firestore.indexes.json` 에 복합 인덱스 5개.

**팀 범위 화면에 필요한 복합 인덱스** — 활동 목록은 아래 인덱스를 사용한다.

- `activities`: `teamId` ASC + `date` DESC

거래처·영업현황은 전사 공유로 단일 정렬하며, 기존 팀 복합 인덱스는 호환을 위해 남겨둔다.

예비 2개(현재 미사용, 단계별 필터링을 서버로 옮길 때용):

- `deals`: `stage` ASC + `updatedAt` DESC
- `activities`: `date` DESC + `createdAt` DESC

감사 로그는 `at` 단일 정렬이라 자동 인덱스로 충분하다.

## 알아둘 불일치

1. **`COLLECTION_PREFIX` 를 규칙과 인덱스가 모르고 있다.** ⚠️ (미해결)
   앱은 `collectionName()` 으로 접두사를 붙여 읽고 쓰는데, `firestore.rules` 의
   `match /customers/{id}` 와 `firestore.indexes.json` 의 `collectionGroup` 은
   접두사 없는 이름으로 고정돼 있다. `VITE_COLLECTION_PREFIX` 를 설정하면 모든 요청이
   `match /{document=**}` 의 `if false` 로 떨어져 앱 전체가 죽는다.
   → 접두사를 쓸 계획이면 규칙 경로부터 함께 바꾸거나, 기능을 걷어낼 것.

2. **팀별 범위 이전 데이터에는 `teamId` 가 없다.**
   공유 거래처·영업현황 목록에서는 보이지만 팀 대시보드·활동·거래에는 집계되지 않는다.
   팀 관리 → **기존 데이터 팀 배정** 에서 한 번 채워야 한다(`assignMissingTeam`).

3. **영업자별 목표는 관리자만 정한다.**
   팀장에게 열려면 `settings/ownerTargets` 를 팀별 문서로 쪼개야 한다 —
   지금 구조는 한 문서에 전 사원 할당이 들어 있어, 팀장에게 쓰기를 열면
   남의 팀 할당까지 덮어쓸 수 있다.
